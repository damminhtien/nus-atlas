Data-centric consistency models

Causal consistency

Causal consistency

▶Implementation of the FIFO-total order broadcast in linearizability

and sequential consistency is expensive.
▶Causal consistency only requires causally related Write requests to

be seen in the same order by all processes.
▶The causal precedence between operations is defined by

1
If two operations op1 and op2 are on the same process, and
the invocation of op2 is after the response of op1, then op1
happens before op2.

![pymupdf:22:7](pymupdf:22:7)

2
A Write operation happens before a Read operation on another
process if the Read returns the value written by the Write.

![pymupdf:22:9](pymupdf:22:9)

3
op1 →op3 if op1 →op2 and op2 →op3.
▶Definition: For any R(x, a), there exists a W(x, a) happening

![pymupdf:22:11](pymupdf:22:11)

before it, and there are no writes W(x, ·) happening in between.

Data-centric consistency models

Eventual consistency

Implementation

▶All Reads return the local replica immediately.
▶On receiving a Write request from application, perform a FIFO

broadcast of the request to all processes.
▶On receiving a Write request from network, compare the timestamp

of the message with the local timestamp.

▶If one happens before the other, write the newer value to the

variable.
▶Otherwise, try to merge the writes. If they are not mergeable,

keep both versions and leave the conflict to the users to resolve.

Read and write concerns

Read concern:

▶"majority": The query returns the data that has been

acknowledged by a majority of the replica set members.
▶"local": The query returns data from the instance with no

guarantee that the data has been written to a majority of the replica
set members.

Write concern:

▶"majority": The query requests that the Write operation has been

applied to a majority of the members.
▶"{ w: 1 }": The query guarantees that the Write operation has

propagated to the primary.

Digest reads and read repair

To reduce network traffic, the coordinator does not initially request the
full row from every replica.

Coordinator
−→
Replica 1: request full data
−→
Replica 2: request digest
−→
Replica 3: request digest

A digest is a compact hash of the requested data.

▶If the digests agree, the replicas contain the same data and the

coordinator returns the full-data response to the client.
▶If the digests disagree, the coordinator requests the full data from

the replicas and reconciles the versions, usually using timestamps.
▶The newest version is returned to the client and sent to stale

replicas. Updating those replicas is called read repair.

digest mismatch =⇒fetch full versions =⇒reconcile and repair
